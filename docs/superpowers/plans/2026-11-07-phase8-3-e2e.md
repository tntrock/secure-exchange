# Phase 8.3: Browser End-to-End Tests Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Drive every screen of secure-exchange in a real Chromium against the real compose stack, locally with one command and in CI on every non-docs PR (spec §4).

**Architecture:**
- A self-contained `e2e/` Node project (Playwright test runner) beside `web/`.
- `scripts/e2e.sh`, modelled on `scripts/smoke.sh`, brings up the full compose stack under its own project name with a mailpit override, waits for health, runs Playwright, and always tears down.
- Tests create their own data through the UI or the public API, and read mail (OTP codes, invitations) from the mailpit API.
- A separate workflow file runs it in CI.

**Tech Stack:**
- Test runner: `@playwright/test` (Chromium only), TypeScript.
- Stack: docker compose (app, worker, postgres, clamav, caddy, mailpit).
- OIDC test: Dex as the mock IdP.

**Spec:** `docs/superpowers/specs/2026-11-07-phase8-release-design.md` (§4). Parent: `docs/superpowers/specs/2026-10-24-secure-exchange-design.md` (§9 testing; e2e main flows at line ~258).

## Global Constraints

- **Chromium only.** Pin exact versions in `e2e/package.json` (no `^`/`~`), commit `e2e/package-lock.json`.
- **No fixed sleeps** (`waitForTimeout` is banned). Wait on page conditions (`expect(...).toBeVisible()`, `toHaveURL`, `waitForResponse`) or poll mailpit/API with `expect.poll`.
- **Self-contained tests.** Every test creates the data it needs, with unique emails per test (e.g. `` `${test.info().testId}-${Date.now()}@e2e.test` ``), and does not depend on another test's order. Tests may run in parallel workers within one stack. Anything global (site rules) runs in a `test.describe.configure({mode: "serial"})` file that restores the rules in `afterAll`.
- **UI language.** Assert on user-visible text through the en locale: the tests set the UI to English once via the language switch or `localStorage` before navigation. Exception: the one zh-TW assertion in the language-switch test.
- **Stack config.**
  - Ports must not collide with the dev stack or `smoke.sh`: HTTPS `59443`, HTTP `59080`, mailpit UI/API `59025`. Project name `sxe2e`.
  - `smoke.sh` and `e2e.sh` both refuse to run when `./.env` exists. Neither may delete a user's `.env`.
- **Trust.** Playwright `ignoreHTTPSErrors: true` (Caddy's internal CA for `localhost`).
- **Third-party GitHub Actions are pinned to a commit SHA**, with the version in a trailing comment, like the existing `ci.yml`.
- **Docs.** Add a short "End-to-end tests" subsection to the README development section, in zh-TW in `README.md` and English in `README.en.md`: the command, prerequisites, and how to open the trace.
- Commit trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A flaky test is a failed test.** Every wait is on a condition. Mail lookups filter by recipient *and* by a timestamp or subject. Nothing relies on "the newest mail in the box", because tests run in parallel.
2. **Teardown always runs:** on test failure, on Ctrl-C, and on a failed `up`. Volumes are removed and the temporary `.env` is deleted, and a pre-existing `.env` is never touched.
3. **A failing CI run leaves something to debug:** the Playwright HTML report and traces, plus `docker compose logs` of app and worker, uploaded as artifacts.
4. **The rules-changing tests restore the site rules** even when an assertion fails (`afterAll`/`finally`), so other tests running afterwards see defaults.
5. **ClamAV signature download** must not make CI flaky or slow. The DB volume is cached between runs, and the scan wait has a generous but bounded timeout with a clear failure message.

## Rulings

- **No LDAP e2e.** There is no lightweight LDAP mock worth the maintenance, and the LDAP path is covered by Go tests against a stub. The admin manual already says LDAP was not tested against a real AD. Recorded in the README e2e subsection.
- **One OIDC e2e via Dex (Task 5).** If, after the implementer's honest attempt, the issuer-hostname problem (browser and app must both reach the *same* https issuer URL) can't be made reliable, the task ends with the OIDC spec skipped (`test.skip` with a reason) and a note in the README. That is acceptable per spec §4.
- **e2e is not a required check yet** (spec §4). The workflow runs on PRs and pushes to main.

- Modify: `.gitignore` (`e2e/node_modules`, `e2e/test-results`, `e2e/playwright-report`, `.e2e-clamav/`), `README.md`, `README.en.md`

**Interfaces (produced, used by every later task):**
- `scripts/e2e.sh [playwright args...]`
  - Writes a temporary `.env`: admin `admin@e2e.test` / generated password, `SX_DOMAIN=localhost`, `SX_HTTP_PORT=59080`, `SX_HTTPS_PORT=59443`, generated master key.
  - Runs `docker compose -p sxe2e -f docker-compose.yml -f docker-compose.e2e.yml up -d --build`, then waits for `https://localhost:59443/healthz` = `ok` (≤ 3 min) and for clamd to answer.
  - Exports `E2E_BASE_URL`, `E2E_MAILPIT_URL`, `E2E_ADMIN_EMAIL`, `E2E_ADMIN_PASSWORD`, then runs `npx playwright test "$@"` in `e2e/`.
  - On any exit, dumps `docker compose logs app worker` to `e2e/test-results/compose.log` and runs `down -v`. It removes only the `.env` it created.
  - `E2E_KEEP=1` skips teardown for debugging.
- `docker-compose.e2e.yml`
  - Adds `mailpit` (`axllent/mailpit:v1.33`, UI on `59025`, network `sx`) and points `app` SMTP at it, as `docker-compose.smoke.yml` does.
  - Bind-mounts `./.e2e-clamav:/var/lib/clamav` for clamav, so CI can cache signatures.
- `mail.ts`
  - `waitForMail(to: string, opts: {subject?: RegExp; since: Date; timeout?: number}): Promise<{subject: string; text: string}>` polls `GET /api/v1/search?query=to:"<to>"` and returns the first message newer than `since` that matches.
  - `extractCode(text: string): string` returns the 6-digit code after `驗證碼是：` or `verification code is:`.
  - `extractLink(text: string, path: RegExp): string`.
- `totp.ts`: `totp(secretBase32: string, at = Date.now()): string` implements RFC 6238 (SHA-1, 30 s, 6 digits) with `node:crypto`. No dependency.
- `api.ts`: `loginApi(request, email, password, totpSecret?)`, plus thin wrappers for the seeding calls later tasks need. Reuse the exact request shapes from `scripts/smoke.sh` and `web/src/api.ts`, including the `Origin` header the server requires.
- `fixtures.ts`: a Playwright `test` extended with:
  - `adminPage`, a signed-in admin page;
  - `staff(name)`, which creates a local staff account through the admin UI or API invite, completes activation from the mail, signs in, and returns `{page, email, password}`;
  - `uniqueEmail(tag)`.

  If the initial admin must enrol TOTP, the fixture enrols once per worker and caches the secret.

- [ ] **Step 1:** Write `e2e/tests/auth.spec.ts`:
  - The admin signs in and lands on `/files`.
  - A wrong password shows the "invalid" message.
  - Sign out returns to `/login`.
  - Switching the language to 繁體中文 changes the login button text, then switching back works.
  - A deep link `/shares` while signed out goes to `/login`, and after signing in lands on `/shares`. This pins PR 8.2's return path.
- [ ] **Step 2:** Run `scripts/e2e.sh tests/auth.spec.ts`. Expected: FAIL (helpers or script missing), then implement until PASS.
- [ ] **Step 3:** Run it twice more back to back, plus once with `--repeat-each=3`. Expected: all PASS. This guards against flakes.
- [ ] **Step 4:** Commit `test(e2e): Playwright scaffold, stack script, auth spec`.

### Task 2: Main flow A — share → verify → view → download → trace

**Files:** Create `e2e/tests/share-flow.spec.ts`, plus small fixture files under `e2e/fixtures/` (a 2-page PDF or `.txt`, and a PNG ≥ 192 px generated at test time or committed, < 50 KB).

**Interfaces:** Consumes the Task 1 helpers.

- [ ] **Step 1:** Write the test.
  1. Staff uploads a `.txt` or PDF through the Files page file picker and waits until the preview is ready (the row's status changes).
  2. Staff opens the share dialog (keyboard: Esc closes it, then reopen), shares with `uniqueEmail` with download allowed and watermark on, and lands on the share detail page.
  3. In a **new browser context**, the recipient opens the invitation link from mailpit, requests a code, enters it from mailpit, and sees the file list.
  4. View opens the viewer; a rendered page image is visible; Esc closes it and focus returns to the View button.
  5. Download triggers a browser download (`page.waitForEvent("download")`), and the file is saved.
  6. The admin opens `/admin/trace`, uploads the downloaded file, and sees a result row naming the recipient email.
  7. Repeat 5–6 for the PNG, so the invisible/visible image mark path is traced.
- [ ] **Step 2:** Run `scripts/e2e.sh tests/share-flow.spec.ts` until PASS, then 3× repeat as in Task 1.
- [ ] **Step 3:** Commit `test(e2e): share → verify → view → download → trace`.

### Task 3: Main flow B and vendors — upload request → external upload; vendor lifecycle

**Files:** Create `e2e/tests/upload-request.spec.ts`, `e2e/tests/vendor.spec.ts`.

- [ ] **Step 1:** Write the upload-request test.
  1. Staff creates an upload request on `/requests` for `uniqueEmail`.
  2. In a new context, the uploader opens the link from mail, verifies with the mailed code, and uploads a small clean file.
  3. The page shows it uploaded or scanning.
  4. `expect.poll` (≤ 5 min, clear message) until the staff's request detail shows the file as clean.
  5. Staff can download it.
- [ ] **Step 2:** Write the vendor test.
  1. Staff invites a vendor on `/vendors`. If `SX_VENDOR_CREATION` defaults to approval, the admin approves it on the pending list.
  2. In a new context, the vendor opens `/invite/<token>` from mail, sets a password, and enrols TOTP. The secret is read from the page's text secret (not the QR code) and the code comes from `totp()`.
  3. The vendor lands on `/vendor/shares`.
  4. Staff shares a file to the vendor, and the vendor sees it and downloads it.
  5. The vendor uploads a file to staff via `/vendor/upload`, and staff sees it after the scan.
  6. Staff disables the vendor, and the vendor's next navigation goes to `/login`.
- [ ] **Step 3:** Run both specs until PASS, then 3× repeat.
- [ ] **Step 4:** Commit `test(e2e): upload request and vendor lifecycle`.

### Task 5: OIDC login against Dex

**Files:** Create `e2e/dex/config.yaml`, `e2e/tests/oidc.spec.ts`. Modify `scripts/e2e.sh`, `docker-compose.e2e.yml`.

**Interfaces / design:**
- Issuer: `https://dex.localhost:59556/dex`.
- `e2e.sh` generates a throw-away self-signed cert for `dex.localhost` with `openssl` into a temp dir and mounts it into Dex. It sets `SX_OIDC_CA` to that cert and `SX_OIDC_ISSUER`, `SX_OIDC_CLIENT_ID=sx-e2e` and `SX_OIDC_CLIENT_SECRET` (random) in the temp `.env`.
- Dex service: `ghcr.io/dexidp/dex:<pinned tag>`, TLS on `59556`, published as `59556:59556`, with network alias `dex.localhost` on `sx`, so the app container and the host browser both resolve `dex.localhost:59556`. Chromium resolves `*.localhost` to loopback.
- Dex uses a static client with redirect URI `https://localhost:59443/api/auth/oidc/callback`, a static password user `oidc-user@e2e.test`, and `enablePasswordDB: true`.
- The app's config validation requires https: this design satisfies it.

- [ ] **Step 1:** Write the test.
  1. The login page shows the SSO button.
  2. Clicking it goes to the Dex login form; fill in the static user and land on `/files` signed in as that email.
  3. The TOTP link is absent (external account).
  4. Sign out.
- [ ] **Step 2:** Run until PASS, then 3× repeat. If the app container cannot resolve or reach `dex.localhost:59556` after a genuine attempt (aliases, `extra_hosts`), apply the ruling: `test.skip(true, "<reason>")`, a README note, and report `DONE_WITH_CONCERNS`.
- [ ] **Step 3:** Commit `test(e2e): OIDC sign-in via Dex`.
