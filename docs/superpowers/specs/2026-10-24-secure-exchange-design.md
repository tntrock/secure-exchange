# secure-exchange 設計文件

日期：2026-10-24
狀態：已過審閱，待使用者核可

## 1. 目的與動機

企業對外交換文件目前靠兩種方式：

- **Email 附件**：受信箱大小限制，大檔案寄不出去。
- **加密壓縮檔 + 另寄密碼**：流程繁瑣，密碼和檔案走同一條管道，安全性也有限。

secure-exchange 是一套**開源、self-host** 的企業檔案交換平台，取代上述做法：檔案留在企業自己的伺服器上，對外以連結分享，由平台負責身分驗證、存取控制、浮水印與外流溯源。

成功的樣子：員工上傳檔案、填收件人、按送出，就完成了一次安全的對外分享；外部對象點連結、收驗證碼、在瀏覽器裡看到檔案；管理員能以全公司規則約束分享行為，事後能追查任何一份外流文件的來源。

## 2. 目標、非目標、反目標

### 目標
- 內 → 外的檔案分享（一次性分享，或分享給廠商帳號）。
- 外 → 內的檔案收件（上傳請求連結，或廠商帳號直接上傳）。
- 預設「僅能線上檢視」：原始檔不離開伺服器。
- 浮水印與外流溯源。
- 管理員可設定強制規則。
- 完整稽核紀錄。
- 以 Docker Compose 一鍵部署。
- v1.0 一次到位，包含本文所有功能（實作可分階段，見 §11）。

### 非目標
- 不做「下載後仍受控」的 DRM（例如下載後仍需連線驗證才能開啟）。已和使用者討論過，決定不做。
- 不防截圖與手機翻拍：這在技術上做不到，改以浮水印嚇阻並溯源。
- 不做 SaaS 多租戶：一套部署服務一個組織。
- 不做線上協作編輯。

### 反目標（技術上能跑也算失敗）
- 「僅能線上檢視」的分享，原始檔或可還原原始檔的資料被送到瀏覽器。
- 浮水印只是前端疊加的一層 DOM／CSS，用開發者工具就能移除。
- 管理員的強制規則能被員工繞過，包括直接呼叫 API。
- 驗證碼可以被暴力猜測。
- 部署需要大量手動設定才能跑起來。

## 3. 角色

| 角色 | 說明 | 登入方式 |
|---|---|---|
| 內部員工 | 上傳、分享、建立收件連結、查看自己分享的紀錄 | 本機帳號（可開 TOTP），或 LDAP/AD、OIDC |
| 管理員 | 員工權限，加上系統設定、強制規則、使用者管理、全站稽核、外流溯源 | 同上 |
| 廠商帳號 | 長期往來的外部對象，由員工或管理員建立 | 帳號密碼 + **強制 TOTP** |
| 一次性收件人 | 不需註冊，由分享名單指定 | Email 驗證碼 |
| 外部上傳者 | 透過上傳請求連結上傳檔案，不需註冊 | Email 驗證碼（見 §5.3） |

## 4. 已決定事項（使用者決定）

1. **一次性分享只用「收件人名單 + Email 驗證碼」**。不做專屬免驗證連結，不做共用密碼，不做網域白名單。
2. **廠商帳號**使用 TOTP 雙因素驗證。
3. **預設僅能線上檢視**；寄件者可針對單一分享選擇允許下載。
4. **檔案類型不固定**。分享設為「僅能線上檢視」但檔案無法預覽時，**建立分享時直接擋下**，提示寄件者改為允許下載；系統**不會**自動開放下載。
5. **浮水印由寄件者在每次分享時決定開或關**（管理員可強制開啟）。
6. **檔案標記指的是追蹤記號**：下載出去的檔案帶有追蹤碼，外流時能查出來源。
7. **管理員可設定強制規則**。
8. **v1.0 包含完整功能**。
9. 專案名稱 `secure-exchange`，GitHub 公開 repo。
10. 技術選型交給 AI 決定，後續開發與維護也由 AI 負責。

## 5. 功能

### 5.1 一次性分享（內 → 外）

建立分享時，寄件者設定：
- 檔案：一個或多個。
- 收件人 email 名單：一或多人。
- 存取模式：僅線上檢視（預設）／允許下載。
- 浮水印：開／關。
- 有效期限、檢視次數上限（選填）。
- IP 限制：允許的 IP 或 CIDR 網段（選填）。
- 附言。

送出後，系統寄邀請信給每位收件人，信中只有連結，不含檔案。

收件人開啟流程：點連結 → 輸入自己的 email → 系統確認在名單內才寄 6 位數驗證碼 → 輸入驗證碼 → 取得該分享的工作階段（session）→ 檢視或下載。

- 不在名單內的 email：回應和名單內的 email 一樣（「若您在名單中，將收到驗證碼」），不透露名單內容。
- 驗證碼：有效 10 分鐘、只能使用一次、最多嘗試 5 次，並對 email 與 IP 限制頻率。
- 寄件者可以隨時撤銷整個分享，或撤銷名單中的某一位。
- 寄件者可以事後新增收件人。

### 5.2 分享給廠商帳號

寄件者選擇廠商帳號作為收件人，不必走驗證碼流程。廠商登入後，在「分享給我的」清單中看到所有檔案。其他規則（檢視模式、浮水印、期限、IP）和一次性分享相同。

一個分享可以同時包含 email 收件人與廠商帳號。

### 5.3 收件（外 → 內）

**上傳請求連結**：員工建立連結並設定：
- 指定上傳者的 email 名單（**我的決定**：沿用一次性分享的驗證碼機制，以符合使用者「只用驗證碼」的安全要求）。
- 有效期限、檔案數與總大小上限、允許的副檔名。
- 附言。

上傳者驗證後即可上傳，檔案直接進入該員工的空間；員工會收到通知。

**廠商帳號**：可以直接上傳給指定的員工，不需要連結。

所有外部上傳的檔案都要經過 ClamAV 掃毒（**我的決定**）。掃到病毒的檔案會被隔離，不讓員工下載，並通知員工與管理員。

### 5.4 線上檢視

核心原則：**送到瀏覽器的只有伺服器端算圖後的圖片（或轉碼後的串流），浮水印在伺服器端直接畫進像素。**

| 類型 | 處理方式 |
|---|---|
| PDF | 逐頁算成圖片 |
| Word / Excel / PowerPoint / ODF | LibreOffice 轉成 PDF，再逐頁算成圖片 |
| 圖片（jpg/png/gif/webp/tiff/bmp…） | 正規化成圖片 |
| 純文字、程式碼、CSV | 算成圖片頁面 |
| 影片 | 轉成 HLS 串流，浮水印燒進畫面（**我的決定**：上傳時先切好無浮水印的片段，檢視時依請求逐段即時燒入該檢視者的浮水印，並在 session 內快取；不必每位檢視者都完整轉檔一次） |
| 其他（CAD、壓縮檔、執行檔…） | 無法預覽 |

- 檢視器只顯示一頁一頁的圖片，提供縮放與翻頁。不提供文字選取。
- 浮水印內容：檢視者身分（email 或廠商帳號）、IP、時間、追蹤碼。以半透明斜向平鋪在整個畫面上。
- 浮水印關閉時，檢視器仍然顯示算圖後的圖片，只是不畫浮水印。原始檔一樣不送到瀏覽器。
- 算圖結果可以快取：快取無浮水印的底圖，浮水印在每次請求時即時疊加。
- 檔案上傳時就判斷能否預覽，並在背景完成轉檔；轉檔失敗的檔案也標記為「無法預覽」。

### 5.5 下載與追蹤標記

只有分享設為「允許下載」時才能下載。每次下載都會產生一組唯一的**追蹤碼**，記錄「追蹤碼 ↔ 分享 ↔ 下載者 ↔ 時間 ↔ IP ↔ 下載檔的 SHA-256」。

| 類型 | 浮水印開 | 浮水印關 |
|---|---|---|
| PDF | 每頁加可見浮水印，並在中繼資料與隱藏文字層寫入追蹤碼 | 原檔，並在中繼資料寫入追蹤碼 |
| 圖片 | 可見浮水印 + 不可見浮水印（追蹤碼） | 原檔 + 不可見浮水印 |
| Office | **轉成加浮水印的 PDF**，對方拿不到可編輯的原檔 | 原檔，並在文件屬性寫入追蹤碼 |
| 其他 | 無法加浮水印，給原檔 | 原檔 |

- 「其他」類型無法嵌入標記，只能靠「誰下載了」的紀錄和檔案指紋比對。介面上要讓寄件者知道這一點。
- **管理員強制浮水印時，無法加浮水印的情況**（使用者決定：由管理員設定）。管理員可以選擇以下其中一種處理方式：
  - **阻擋**：這類檔案不能設為允許下載；Office 檔只能以加浮水印的 PDF 提供下載。
  - **允許並警告**：這類檔案提供原檔下載，只靠下載紀錄與嵌入的追蹤碼追蹤，建立分享時清楚警告寄件者。Office 檔可以提供原檔。

  受影響的檔案包括「其他」類型，以及加浮水印後會變成 PDF 的 Office 檔。
- 不可見浮水印（圖片）先用基本、可靠的頻域方法，要能撐過輕度 JPEG 壓縮與縮放。追求更高強韌度不在 v1 範圍內。

### 5.6 外流溯源

管理員上傳一份疑似外流的檔案，系統依序嘗試：
1. 讀取中繼資料或文件屬性中的追蹤碼；
2. 讀取 PDF 隱藏文字層中的追蹤碼；
3. 讀取圖片的不可見浮水印；
4. 用 SHA-256 比對下載紀錄。

找到就顯示對應的分享、下載者、時間與 IP；找不到就明確說明「無法判定」。

截圖、翻拍類的外流只能靠人眼辨識畫面上的可見浮水印（追蹤碼要印得夠清楚，方便人工輸入查詢）。系統要提供「輸入追蹤碼查詢」的功能。

### 5.7 管理員強制規則

全系統層級設定，員工無法覆蓋（**API 層也要檢查，不只是前端**）：
- 浮水印：強制開啟 / 由員工決定。
- 下載：一律禁止 / 由員工決定。
- 分享最長有效天數；預設有效天數。
- 單一檔案大小上限、單一分享總大小上限。
- 收件人網域封鎖清單、允許清單（設了允許清單就只能分享給這些網域）。
- 預設 IP 限制：例如全站只允許特定網段開啟。
- 外部上傳：允許的副檔名、大小上限。
- 員工儲存空間配額。
- 檔案保留期限：分享過期後多久自動刪除檔案。

員工建立分享時，被鎖定的選項顯示為灰色，並標示「由管理員設定」。

**規則收緊時的既有分享**（**我的決定**）：規則在每次檢視與下載時都重新檢查，不只在建立分享時檢查。既有分享違反新規則時，以較嚴格的規則為準（例如強制浮水印後直接加上浮水印、禁止下載後只能線上檢視、封鎖網域後該收件人無法存取）。系統會通知受影響分享的建立者，但不會自動刪除分享。

### 5.8 稽核紀錄

記錄所有安全相關事件：登入（成功／失敗）、上傳、建立／修改／撤銷分享、寄出驗證碼、驗證成功／失敗、檢視（含頁數）、下載、外部上傳、規則變更、使用者管理、溯源查詢。

每筆紀錄包含：時間、行為者、IP、User-Agent、對象、結果。

- 只能新增，不能修改或刪除。**我的決定**：每筆紀錄帶前一筆的雜湊，形成雜湊鏈，可以驗證有沒有被竄改。雜湊鏈只能偵測繞過應用程式的竄改；若要防範擁有資料庫完整權限的人，需另外即時匯出到外部系統，因此提供 syslog 匯出功能作為選項。
- 管理員能篩選與匯出 CSV；員工能看到自己分享相關的紀錄。

### 5.9 通知（Email）

- 收件人第一次開啟分享。
- 收件人下載。
- 外部上傳完成。
- 分享即將到期（選配）。
- 掃毒發現病毒。

員工可以在個人設定中關閉部分通知。

### 5.10 帳號管理

- 本機帳號：密碼使用 argon2id 雜湊，可選用 TOTP；管理員可設定全站強制 TOTP。
- LDAP/AD：可設定登入綁定與群組對應（某群組自動成為管理員）。
- OIDC：可設定 Entra ID、Google Workspace、Keycloak 等。
- 廠商帳號：由員工建立（需管理員允許），系統寄邀請信，首次登入時設定密碼與 TOTP。廠商帳號有到期日，可停用。
  - **我的決定**：一個廠商帳號對應一個人。同一家公司的多個帳號，可以歸在同一個「廠商組織」底下，方便選取與管理。
  - 「需管理員允許」是一個全站設定，有三種選項：員工可以自由建立帳號、建立後要經管理員核准才生效、只有管理員能建立帳號。
  - 任何員工都可以分享給任何啟用中的廠商帳號。
  - 廠商直接上傳時，只能選擇曾經分享給他、或建立他帳號的員工，不會看到完整的員工名單。
- 首次部署時，由環境變數或首次設定精靈建立第一位管理員。

## 6. 安全模型

- **傳輸**：全程 HTTPS。Docker Compose 內附反向代理（**我的決定**：Caddy，可自動申請憑證），也支援放在企業既有的反向代理後面。
- **儲存加密**：信封加密。每個檔案（含轉檔產物與快取圖片）有獨立的資料金鑰，以 AES-256-GCM 加密；資料金鑰再由主金鑰加密後存進資料庫。主金鑰由環境變數或金鑰檔提供，不寫進資料庫。v1 要提供主金鑰輪替的機制。
- **分享連結**：連結中的 token 至少 128 bit 隨機值；資料庫只存雜湊。
- **Session**：HttpOnly、Secure、SameSite cookie；外部收件人的 session 只綁定單一分享，有效時間短。
- **IP 判斷**：放在反向代理後時，要有「信任的代理位址」設定，才會採信 X-Forwarded-For。
- **頻率限制**：登入、驗證碼請求、驗證碼驗證、上傳都要限制頻率。
- **CSRF、CSP、安全標頭**：都要設定。
- **管理員權限**（使用者決定）：管理員可以開啟任何員工的檔案與分享內容。每次開啟都寫入稽核紀錄。
- **轉檔隔離**：LibreOffice 等轉檔程式跑在獨立容器中，不開放網路，並設定資源與時間上限，防止惡意檔案造成影響。

## 6.1 規模與大檔案（使用者決定：單檔可達數十至數百 GB）

大檔案是本產品存在的主要理由，以下各點都是必要的：

- **可續傳的分塊上傳**（**我的決定**：採用 tus 協定）。斷線後可以從中斷處繼續上傳，網頁和廠商上傳都支援。
- **分塊串流加密**：檔案切成固定大小的區塊（例如 1 MiB），每個區塊各自用 AES-256-GCM 加密，並把區塊序號放進驗證資料，防止區塊被重新排列或截斷。不可以一次把整個檔案讀進記憶體。
- **串流下載**：支援 HTTP Range，可以續傳下載；伺服器邊解密邊送出。
- **S3 multipart**：S3 後端要使用 multipart 上傳。
- **完整性**：上傳完成後在伺服器端計算 SHA-256，下載頁顯示，方便對方核對。
- **預覽上限**：大檔案不一定要完整算圖。可以設定預覽的大小、頁數與影片長度上限（**我的決定**：預設值由實作者依測試結果訂定，管理員可調整）。超過上限就視為「無法預覽」，適用 §4 第 4 點的阻擋規則。
- **追蹤標記的成本**：為下載檔加浮水印或嵌入追蹤碼時，會為每位下載者產生一份新檔案。超大檔案要以串流方式處理，不可以完整暫存。如果做不到，就視為無法加標記，適用前述的管理員設定。
- **使用者規模**（**我的決定**）：使用者沒有指定，所以以數百位內部使用者、數十人同時檢視為設計目標。架構上 app 與 worker 都可以水平擴充，但 v1 不追求叢集部署。
- **部署環境**（使用者決定）：伺服器可以連外網。Caddy 自動申請憑證、ClamAV 自動更新病毒碼、對外寄送 SMTP 都假設可以連網。也保留自備憑證的選項，但不支援完全離線的部署。

## 7. 技術選型（我的決定）

| 元件 | 選擇 | 理由 |
|---|---|---|
| 後端 | Go | 單一執行檔，部署簡單；標準函式庫的 crypto 與 HTTP 完整；AI 撰寫與維護都很熟 |
| 前端 | React + TypeScript + Vite | 生態最大，AI 最熟；編譯後以 `embed` 嵌入 Go 執行檔 |
| 資料庫 | PostgreSQL | |
| 檔案儲存 | 本機磁碟或 S3 相容儲存（MinIO 等），設定擇一 | |
| 轉檔 | LibreOffice（headless）、PDF 算圖工具、FFmpeg | 跑在獨立的 worker 容器 |
| 掃毒 | ClamAV | |
| 背景工作 | 以 PostgreSQL 當工作佇列 | 不另外引入 Redis 或訊息佇列 |
| 部署 | Docker Compose：app、worker、postgres、clamav、caddy | |

PDF 算圖、浮水印與 PDF 修改要選用的函式庫，以及授權相容性（專案授權建議 AGPL-3.0 或 Apache-2.0，見 §10），留給實作者在規劃時確認。

## 8. 部署

- `docker compose up -d` 就能啟動，再搭配一份 `.env` 範本（網域、SMTP、主金鑰、初始管理員）。
- SMTP 設定是必要的，因為驗證碼要靠 email 寄送。
- 提供資料備份與還原說明（資料庫 + 檔案儲存 + 主金鑰，並強調主金鑰遺失就無法解密檔案）。
- 版本升級時自動執行資料庫 migration。

## 9. 品質要求

- 安全路徑（權限檢查、強制規則、驗證碼、連結 token、加解密、浮水印）都要有自動化測試。
- 端對端測試涵蓋主要流程：分享 → 驗證 → 檢視 → 下載 → 溯源；上傳請求 → 外部上傳。
- GitHub Actions：測試、lint、建置 Docker image。
- README 提供繁體中文與英文版本，內容包含部署教學。

## 10. 留給實作者決定
