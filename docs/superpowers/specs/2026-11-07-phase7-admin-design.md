# 第七階段設計：管理員強制規則、管理介面、LDAP/AD、OIDC

日期：2026-11-07。上位文件：[2026-10-24-secure-exchange-design.md](2026-10-24-secure-exchange-design.md)（§3、§5.7、§5.8、§5.9、§5.10、§6）。本文件只寫第七階段新增或修正的決定；與上位文件衝突時以本文件為準。

## 1. 目的與使用情境

- **資安人員**擔任全站管理員：設定強制規則、管理帳號、查看與匯出稽核紀錄、溯源。（使用者說明）
- **一般員工只管自己的資料**，不新增「部門管理員」之類的中間角色。（使用者決定）
- 公司環境有地端 AD 與 Entra ID（AAD）。AD 中被選定的人同步到 AAD，可視為同一批人。（使用者說明）
- 專案是開源的，必須能在沒有 AD 的環境獨立使用，所以**本機帳號一定要能在介面上建立與管理**。（使用者決定）
- 資安團隊使用 Splunk 或 ELK。（使用者說明）

## 2. 目標、非目標、反目標

**目標**
1. §5.7 全部九項強制規則，伺服器端強制執行，每次檢視／下載重新檢查。
2. 管理介面：使用者管理、強制規則、稽核紀錄（篩選、CSV、雜湊鏈驗證）、全站分享瀏覽。
3. 稽核紀錄即時轉送 syslog。
4. 三種登入方式並存：本機、LDAP/AD、OIDC（以 Entra ID 為主要驗證對象）。

**非目標**
- 不做部門層級或委派管理員。
- 禁止下載**沒有例外**：不做「特定員工或群組可豁免」。（使用者決定：太複雜不一定好用）
- 不做跨登入來源的帳號合併。（使用者決定，見 §4.1）
- 不做 LDAP/OIDC 設定的管理介面；這些設定放 `.env`。
- 不做 SCIM 或 AD 帳號預先同步；外部帳號在首次登入時建立。

**反目標**（技術上能跑也算失敗）
- 員工能透過直接呼叫 API 繞過任何一條強制規則。
- 規則收緊後，既有分享仍以舊規則提供下載或無浮水印檢視。
- 外部身分系統（AD/Entra）的使用者，能憑相同 email 登入或接管本機帳號。
- syslog 暫時連不上時遺失稽核紀錄。
- 系統只剩零位可用的管理員（最後一位本機管理員被停用或降級）。

## 3. 強制規則（§5.7）

### 3.1 規則清單

全部都做（使用者決定）。規則存在資料庫的單列設定表中，由管理員在介面修改，**立即生效**，每次修改寫一筆稽核（含修改前後的值）。

| # | 規則 | 值 |
|---|---|---|
| 1 | 浮水印 | 強制開啟 / 由員工決定 |
| 2 | 下載 | 一律禁止 / 由員工決定 |
| 3 | 分享有效天數 | 最長天數、預設天數 |
| 4 | 大小上限 | 單一檔案、單一分享總大小 |
| 5 | 收件人網域 | 封鎖清單、允許清單（設了允許清單就只能分享給清單內網域） |
| 6 | 全站 IP 限制 | CIDR 清單；外部存取（收件人、廠商、外部上傳者）只能從這些網段 |
| 7 | 外部上傳 | 允許的副檔名清單、單檔大小上限 |
| 8 | 員工儲存配額 | 每位員工的位元組上限（0 = 不限） |
| 9 | 檔案保留期限 | 分享結束後幾天自動刪除檔案（0 = 不自動刪） |

### 3.2 套用範圍與語意

- **禁止下載**適用於一次性分享與分享給廠商。員工下載自己的檔案不受影響。（使用者確認）
- **規則收緊時，既有分享以較嚴格者為準**（上位文件 §5.7）：
  - 強制浮水印 → 既有分享檢視時直接加上浮水印。
  - 禁止下載 → 原本允許下載的分享只能線上檢視。
  - 封鎖網域／不在允許清單 → 該收件人無法存取（可驗證身分，但存取被拒，並顯示原因）。
  - 全站 IP 限制 → 與分享本身的 IP 限制**取交集**（兩者都要符合）。
  - 不自動刪除分享；系統寄一封摘要信通知受影響分享的建立者（每位建立者一封，列出受影響的分享與原因）。
- **禁止下載的副作用**：無法預覽的檔案在禁止下載後就完全無法存取。
  - 建立分享時直接擋下（沿用上位文件 §4 第 4 點的錯誤），訊息改為說明「管理員已禁止下載」。
  - 既有分享中這類檔案顯示「此檔案目前無法存取（管理員已禁止下載）」。
- **建立分享介面**：被鎖定的選項變灰並標示「由管理員設定」。天數、大小、網域等限制在送出前於前端提示，但以伺服器檢查為準。
- **外部上傳限制**同時套用於上傳請求（第五階段）與廠商直接上傳（第六階段）。
  - 上傳請求本身已有的 `allowed_exts`、`max_total_bytes` 仍然有效，與全站規則取**較嚴格者**。
  - 在 tus 建立上傳時檢查（檔名副檔名、宣告的長度）。
- **配額**：
  - 計算員工名下未刪除檔案的大小總和，加上進行中上傳的宣告長度。
  - 在 tus 建立上傳時檢查。
  - 外部上傳者與廠商上傳給某員工的檔案計入該員工配額，超過時拒絕並告知「收件人的儲存空間已滿」。**我的決定**
- **保留期限**：
  - 檔案曾被至少一個分享引用，且所有引用它的分享都已過期或撤銷滿 N 天，就由背景工作刪除（軟刪除後清除儲存與預覽產物）。
  - 透過上傳請求收到的檔案，在該請求過期或撤銷滿 N 天後刪除；如果此時檔案仍被某個進行中的分享引用，就等該分享也結束滿 N 天。（使用者決定）
  - 廠商直接上傳的檔案，以及員工自己上傳、從未分享的檔案，不自動刪除。（使用者決定）
  - 刪除寫稽核，actor 為 `system`。
- **與既有環境變數的關係**（**我的決定**）：
  - `SX_SHARE_MAX_DAYS` 只用來給資料庫規則提供初始值，之後以介面設定為準。
  - `SX_MAX_FILE_SIZE` 仍是硬上限，介面上的單檔上限只能更低。

## 4. 帳號與登入

### 4.1 三種登入來源

- 本機、LDAP/AD、OIDC 三種並存，由 `.env` 開關 LDAP 與 OIDC；本機永遠可用。
- **每個登入來源的帳號互相獨立**：同一個人用 AD 與 Entra 登入就是兩個帳號，不合併。（使用者決定）
  - 唯一性改為「登入來源 + 外部識別碼」：LDAP 用 `objectGUID`（或可設定的屬性），OIDC 用 `iss` + `sub`。
  - email 唯一性改為「每個登入來源內唯一」。本機員工與廠商都屬於本機來源，彼此仍不能重複。
  - 外部身分系統的使用者，永遠不會登入到本機帳號，即使 email 相同。
- 登入頁：本機帳號表單、網域帳號（LDAP）表單（若啟用）、「以 Microsoft 登入」按鈕（若啟用，按鈕文字可設定）。**我的決定**

### 4.2 LDAP/AD

- 以服務帳號查詢使用者 DN，再用使用者密碼 bind 驗證。支援 LDAPS 與 StartTLS；不允許明文 bind。
- 首次登入建立帳號（role = staff），之後每次登入更新 email、顯示名稱。
- **管理員群組對應**：`.env` 指定一個群組 DN；成員（含巢狀群組）為 admin，其他人為 staff。每次登入重新判定，被移出群組就降為 staff。
- AD 帳號停用或刪除後無法登入。已登入的 session 每 15 分鐘向 LDAP 重新檢查一次帳號狀態與群組，失效就結束 session。**我的決定**
- **AD 連不上時從嚴**：重新檢查失敗（連線錯誤、逾時）就結束該 session，所有網域帳號（包括網域管理員）都會被登出，直到 AD 恢復。本機管理員不受影響，可以作為救援帳號。（使用者決定）
- 多因素驗證交給公司既有機制；系統不對 LDAP 帳號要求 TOTP。（使用者確認的方向）

### 4.3 OIDC

- 標準 Authorization Code + PKCE 流程，驗證 `state`、`nonce`、ID token 簽章與 `iss`／`aud`。
- 主要以 Entra ID 驗證，但不寫死 Entra；Google Workspace、Keycloak 應能用相同設定接上。
- 首次登入建立帳號（role = staff），之後每次登入更新 email、顯示名稱。
- **管理員對應**：`.env` 指定 claim 名稱與值（預設 claim `groups`）。
  - Entra 的群組過多時會省略 `groups` claim，因此文件建議改用 App Role（claim `roles`）。
- 無法在登入後主動確認帳號狀態，因此 OIDC session 以 `SX_SESSION_TTL` 為上限。**我的決定**
- 多因素驗證交給身分提供者（例如 Entra 條件式存取）；系統不對 OIDC 帳號要求 TOTP。

### 4.4 本機帳號管理

- 管理員在介面建立本機員工或管理員。
  - 系統寄邀請信，對方開連結自行設定密碼（與 TOTP，見下）。
  - 流程與第六階段的廠商邀請相同；可重寄邀請，重寄會使舊連結與舊的待啟用 TOTP 金鑰失效。
- 管理員可對任何帳號：停用／啟用、重設 TOTP（含廠商）。
- 只有本機帳號可以手動改角色。LDAP/OIDC 帳號的角色由群組決定，介面上不可修改。
- **全站強制 TOTP**：一個開關，只套用於本機員工與管理員（廠商本來就強制）。
  - 開啟後，尚未設定 TOTP 的本機帳號下次登入時必須先完成設定才能使用。
- **不能讓系統失去最後一位可用的本機管理員**：停用、降級最後一位啟用中的本機管理員時拒絕。
  - 外部來源的管理員不算，因為 AD/IdP 故障時本機管理員是唯一的救援途徑。
- 初始管理員仍由環境變數建立（上位文件 §5.10）。

## 5. 管理介面

- **使用者**
  - 列表欄位：email、名稱、角色、登入來源、狀態、TOTP、最後登入。
  - 動作：建立本機帳號、停用／啟用、重設 TOTP、改角色（僅本機）、重寄邀請。
- **強制規則**：§3.1 九項與全站強制 TOTP 開關。修改後顯示「受影響的既有分享數」。
- **稽核紀錄**
  - 可依時間範圍、操作者、動作類型、對象篩選，分頁瀏覽。
  - 可匯出 CSV（目前篩選條件下的全部結果，串流輸出）。
  - 「驗證雜湊鏈」按鈕，回報驗證通過的筆數，或第一筆斷鏈的位置。
- **全站分享**：瀏覽所有員工的分享與上傳請求，可開啟內容（上位文件 §6：管理員可以開啟任何員工的檔案與分享，每次開啟寫稽核）並撤銷。
- **廠商核准**、**溯源**：沿用第六、第四階段已完成的頁面，放進同一個管理選單。
- **員工看自己的稽核**：在分享詳細頁顯示該分享相關的紀錄（上位文件 §5.8）。

## 6. 稽核轉送 syslog

- `.env` 設定目的地與傳輸方式（UDP、TCP、TLS；TLS 可指定 CA）。未設定就不轉送。
- 格式：RFC 5424，MSG 為該筆稽核的 JSON（含雜湊），TCP/TLS 使用 octet-counting 分框。Splunk 與 ELK 都能直接接收。
- **不遺失**：
  - 以「已轉送到的最後一筆 id」為游標，背景工作依序送出。
  - 連不上時重試，恢復後從游標繼續補送。
  - 游標存在資料庫，重啟不會重送或漏送。
  - UDP 無法確認送達，文件中說明這一點。
- 送出失敗持續過久時，在管理介面顯示警示。**我的決定**

## 7. 通知偏好（§5.9）

員工可在個人設定關閉以下通知：收件人首次開啟、收件人下載、外部上傳完成。掃毒發現病毒的通知不能關。**我的決定**：§5.9 寫明要有這個功能，而第八階段只排了多語系、文件與端對端測試，所以放在這一階段做。

## 8. 交付方式

拆成五個 PR，依序合併，每個都要能獨立上線：

1. 強制規則與規則管理頁。
2. 使用者管理：本機帳號邀請、強制 TOTP、重設 TOTP、全站分享瀏覽。
3. 稽核頁、CSV、雜湊鏈驗證、syslog 轉送、員工端稽核、通知偏好。
4. LDAP/AD。
5. OIDC。

每個 PR 都要同步更新 `docs/admin-manual.md`、`docs/user-manual.md` 與 `.env.example`，把手冊中「目前要用 SQL」的段落改成介面操作。

## 9. 補充決定（審閱後）

以下都是**我的決定**，除非另外標明。

- **全站 IP 限制**
  - 空清單表示不限制。
  - 擋的範圍是所有外部端點：收件人的著陸頁、驗證碼、檢視與下載；廠商登入與廠商端 API；外部上傳者的全部端點。
  - 員工與管理員不受限，所以設錯網段不會把管理員鎖在外面；介面上提醒「設定後外部使用者只能從這些網段存取」。
  - 來源 IP 沿用既有的 `SX_TRUSTED_PROXIES` 判斷。
- **網域規則**
  - 封鎖清單與允許清單同時設定時，封鎖優先。
  - 規則也套用在廠商帳號的 email 網域：建立廠商、分享給廠商、廠商存取分享，三處都檢查。
- **配額**：軟刪除的檔案不計入配額。
- **稽核順序**：`Append` 在 advisory lock 內取得 id 並寫入，所以 id 順序就是提交順序，syslog 游標可以安全使用 id。
  - 有多個 app 實例時，以 advisory lock 決定由哪一個實例轉送。
  - 雜湊鏈驗證以串流方式逐筆計算，不一次載入整張表。
- **規則收緊通知**：每次儲存規則觸發一次，在背景計算受影響的分享並寄信。介面在儲存後顯示受影響的數量。
- **session 何時失效**
  - 停用或降級本機帳號：立即生效（現有 `requireRole` 每次請求都重讀帳號狀態），並刪除停用帳號的 session。
  - LDAP 帳號最多延遲 15 分鐘（見 §4.2）。
  - OIDC 帳號最多延遲 `SX_SESSION_TTL`。
- **OIDC 身分欄位**
  - 帳號不靠 email 對應（§4.1），email 只作為通知地址與顯示，所以不要求 `email_verified`。
  - 沒有 `email` claim 時，依序改用 `preferred_username`、`upn`。
  - 管理員 claim 是陣列時，只要任一元素相等就算符合。
- **現有資料**：目前只有本機帳號，不需要搬移外部帳號。新增外部識別碼欄位，把 email 唯一索引改為「登入來源 + email」。
- **管理員開啟員工檔案**：只能線上檢視，一律加浮水印（浮水印內容是管理員身分），不提供下載。
- **環境變數初始值**：`SX_SHARE_MAX_DAYS` 只在規則表第一次建立時寫入，之後修改環境變數不會有作用；啟動時如果發現它與資料庫的值不同，就記一筆警告 log。

## 10. 留給實作者

- 資料表結構與 API 設計、前端元件結構。
- LDAP 與 OIDC 函式庫的選擇：Go 生態系中維護良好、授權相容的函式庫，例如 `go-ldap/ldap/v3`、`coreos/go-oidc/v3`。
- 規則快取策略：規則必須在修改後立即生效，所以多個 app 實例之間不可讀到舊值。
- 受影響分享通知信的文字。
- 管理介面的版面設計，沿用現有元件風格。
- syslog 的 facility、severity 對應方式。
