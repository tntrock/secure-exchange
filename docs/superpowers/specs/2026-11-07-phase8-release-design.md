# 第八階段設計：發布前修正、端對端測試、雙語文件、v1.0 發布

日期：2026-11-07。上位文件：[2026-10-24-secure-exchange-design.md](2026-10-24-secure-exchange-design.md)（§11 第 8 項、§9 測試、第 27 行「v1.0 包含規格內所有功能」）。本文件只寫第八階段的決定；與上位文件衝突時以本文件為準。

## 1. 目的與使用情境

- v1.0 有兩種使用者（使用者說明）：
  - **公司內部**：自己部署給同事用。
  - **GitHub 上的陌生人**：下載後自己架設。
- 外部架設者很可能讀不懂中文，也不想自己編譯（Claude 推測，使用者已用下列決定確認）。
- v1.0 是第一次正式發版（上位文件：全部功能完成才發布）。

## 2. 目標、非目標、反目標

**目標**
1. 修掉前七階段累積的待辦小問題中「使用者看得到」與「跟安全有關」的部分（使用者同意這個切法，見 §3）。
2. 用真的瀏覽器跑端對端測試，**涵蓋每一個畫面**，不只兩條主流程（使用者：「每個地方都很重要」）。測試放進 CI。
3. 管理員手冊、使用者手冊、README 都要有**完整的中文版與英文版**（使用者決定）。
4. 發布**包好的 Docker 映像**，讓架設者不必自己 build（使用者決定）。
5. 打 `v1.0.0` tag，發 GitHub Release。

**非目標**
- 內部細節類的待辦（效能、程式碼整潔、測試結構）不在 v1.0 前處理，留在清單上（使用者同意）。
- 不支援中英以外的語言。
- 不做 Helm chart、Kubernetes 範本、安裝精靈。
- 不在真的 AD／Entra 環境做自動測試（CI 沒有這些環境）；文件標明「已用模擬服務測試」。

**反目標**（技術上能跑也算失敗）
- 照英文 README 從零架設，做不到能登入、能分享。
- 映像裡的版本號、文件中的指令、`.env.example` 三者互相對不上。
- 端對端測試偶爾失敗（flaky），讓人習慣性重跑、忽略紅燈。
- 英文文件只翻了一半，或中英兩版描述的功能不一致。
- 發布的映像以 root 身分執行，或內含開發用的金鑰、測試帳號。

## 3. 發布前修正（PR 8.1、8.2）

### 3.1 選取原則

- **選入**：使用者在畫面上會遇到的錯誤或不便、無障礙基本操作、資安或稽核正確性、資料或 session 無限累積。
- **不選**：只影響效能或程式碼整潔、使用者感受不到的項目。
- 清單來源是各階段 PR 的「parked」紀錄。下面兩張表就是完整的範圍，不必再另外去找其他項目。部分項目後續階段可能已經順手修掉，所以**每一項先確認問題仍存在**再修；已修好的在 PR 說明中註記即可。

## 4. PR 8.3：瀏覽器端對端測試

- **工具**：Playwright（Claude 的選擇），只用 Chromium。
- **環境**：
  - 用 compose 起一套完整服務：app、worker、Postgres、mailpit、ClamAV。
  - 驗證碼和邀請信從 mailpit API 取得。
- **涵蓋範圍**：每一個畫面至少走一次正常流程，主流程走完整串。
  1. 主流程 A：登入 → 上傳 → 建分享 → 收件人開信 → 輸入驗證碼 → 線上檢視（看得到浮水印）→ 下載 → 管理員用溯源找回收件人。
  2. 主流程 B：建上傳請求 → 外部的人驗證並上傳 → 掃描完成 → 寄件人看到檔案。
  3. 廠商：邀請 → 啟用並設定 TOTP → 登入 → 看到分享 → 上傳。
  4. 管理後台：規則（改一條規則並確認立即生效）、使用者（邀請、停用）、稽核（篩選、匯出 CSV、驗證雜湊鏈）、全站分享。
  5. 帳號：TOTP 設定、通知設定、登出。
  6. 中英切換：至少一個畫面切換後文字改變。
- **不在瀏覽器測**：
  - 大檔案中斷續傳和 EICAR 病毒判定。這兩項由 `scripts/smoke.sh` 繼續負責，不移除。
  - LDAP 和 OIDC 只在有模擬服務時測（Claude 的選擇：OIDC 以輕量模擬 IdP 測一次完整登入；LDAP 若沒有輕量模擬服務就略過，並在文件註明）。
- **CI**：
  - 新增一個 job，每個 PR 都跑。
  - 失敗時上傳 Playwright trace 和截圖。
  - 先觀察穩定性，連續穩定後才設為 main 的必要檢查。
  - 只改文件（`docs/**`、`*.md`）的 PR 不跑這個 job（Claude 的選擇）。
  - ClamAV 用真的服務，病毒碼資料庫用 actions/cache 快取，避免每次都重新下載（Claude 的選擇）。
- **穩定性**：
  - 不用固定秒數等待，一律等畫面上的條件。
  - 每個測試自己建立需要的資料，不依賴其他測試的執行順序。

## 6. PR 8.5：映像發布與 v1.0

- **映像**（Claude 的選擇）：
  - 位置：GitHub Container Registry。
  - 兩個映像：`ghcr.io/tntrock/secure-exchange`（Dockerfile 的 `app` target）和 `ghcr.io/tntrock/secure-exchange-worker`（`worker` target）。
  - 只建 linux/amd64。worker 需要 LibreOffice 和 ffmpeg，arm64 建置慢且沒驗證過；之後有需求再加。
- **觸發**：推送 `v*` tag 時，由新的 GitHub Actions workflow 建置並推送。
  - 標籤：`1.0.0`、`1.0`、`latest`。
  - 第三方 action 依專案慣例釘在 commit SHA。
- **版本號**：建置時寫進執行檔，從 `/healthz` 以外的地方查得到（例如啟動 log 和管理後台頁尾）。
- **docker-compose.yml**：
  - 預設改用發布的映像，並固定在發布的版本號。
  - 本機 build 改由 `docker-compose.dev.yml` 或 override 檔負責。
- **安全要求**：
  - 映像以非 root 執行。
  - 映像中不含 `.env`、金鑰、測試資料。
  - 發布前用現有 `scripts/smoke.sh` 對**發布的映像**跑一次。
- **GitHub Release `v1.0.0`**：
  - 附上 `docker-compose.yml`、`Caddyfile`、`clamd.conf`、`.env.example` 與各自的 `.sha256`。
  - 版本說明用中英文，列出功能清單、映像名稱、架設步驟連結。
- **發布流程**（Claude 的選擇）：
  1. 推送 `v*` tag 後，同一個 workflow 依序完成以下步驟，任一步失敗就停止，不推送也不發布。
     - 建置兩個映像。
     - 用剛建好的映像跑 `scripts/smoke.sh`。
     - 推送到 ghcr。
     - 產生 `.sha256`，建立 GitHub Release。
  2. 打 tag 前向使用者確認一次。tag 一推出去就會自動發布，所以確認必須在推送之前。
- **版本號一致**（Claude 的選擇）：
  - 版本號只寫在一個地方：repo 根目錄的 `VERSION` 檔。
  - CI 檢查 `docker-compose.yml` 的映像標籤是否等於 `VERSION`。
  - 發布 workflow 檢查 tag 是否等於 `v` 加上 `VERSION`，不一致就失敗。
- **v1.0.0 之前的狀態**：
  - 一般 CI 和 8.3 的端對端測試照常用本機 build，不依賴 ghcr 上的映像。
  - 文件裡的 `docker pull` 指令在 v1.0.0 發布後才有效，這是預期的。
- **發布順序**：8.1 → 8.2 → 8.3 → 8.4 → 8.5。8.5 合併後才打 tag。

## 7. 交付方式

- 五個 PR，每個 PR 一份實作計畫，以 subagent-driven-development 執行。
- 沿用既有 PR 流程：自我審查、CI 綠燈才合併、合併後刪分支。
- 覆蓋率門檻維持 90%。

## 8. 留給實作者決定

- 清理工作的執行間隔與保留期限（合理即可，寫進設定總覽）。
- app 容器的 mem_limit：依程式實際用量估一個值，避免大檔案加浮水印或上傳時記憶體不足，並寫進文件。
- 映像已經以 UID 65532 執行。實作者只要補一個檢查，確認發布的映像不是用 root 跑。
- Playwright 測試的檔案結構與共用 helper。
- 模擬 IdP 的選擇。
- 版本號注入的方式（ldflags 或其他）。
- 英文文件的措辭（以清楚正確為準，不必逐句直譯）。
